Anatomy

The matrix is a root plus nine parts. Each part has one job, so each can be specified, tested and changed on its own. Select a part to outline it on the live instance.

Parts

    Hierarchy

    Why each variant exists
    
    
    
      
    
        
    Plan count: 2 / 3 / 4
    
        
    
          
    2 plans
    Upgrade prompt in account: “your current plan” against the next tier up.
    
          
    3 plans
    Default sales journey: Essential, Extra, Complete.
    
          
    4 plans
    A fourth tier is introduced (Complete Plus covers a connected device). Rows that only that tier includes appear automatically.
    
          
    Limit
    5+ plans is not supported. Use a filtered list instead — comparison breaks down beyond four columns.
    
        
    
      
    
      
    
        
    Price: with / without
    
        
    
          
    With
    Price is known: device already chosen in the journey.
    
          
    Without
    Price depends on a device not yet chosen, e.g. a help article explaining cover levels. The price row is removed rather than filled with placeholders.
    
          
    Rule
    All plans show price or none do. Mixed rows read as missing data.
    
        
    
      
    
      
    
        
    Recommendation: with / without
    
        
    
          
    With
    The business has a defensible default (most chosen, best fit for this device). One plan gets a filled badge, a tinted column and the only primary CTA.
    
          
    Without
    Regulated or neutral contexts where steering is inappropriate. All CTAs carry equal weight.
    
          
    Rule
    Never more than one recommendation.
    
        
    
      
    
      
    
        
    Features: grouped / simple
    
        
    
          
    Grouped
    9+ features. Groups give the customer landmarks and a sticky “where am I” heading.
    
          
    Simple
    Short lists (≤ 8 rows) such as an in-app upgrade sheet, where headings add more height than help.
    
          
    Rule
    Same data shape either way — simple mode flattens groups in order.
    
        
    
      
    
    
    
    
    Deliberately not variants: colour themes, icon sets, card-style columns, horizontal-scrolling tables, and per-plan custom layouts. Each would multiply the surface area without solving a product requirement, and most would weaken scanning.
    
  
    

    



    
  
    
    
    States
    
    
    Interaction states (the customer did something) are kept visually distinct from system states (the business is telling the customer something). Recommendation uses the accent colour; selection uses ink. They can co-exist on one plan.
    
  
    

  
    
    
    CTA
    
    
    Hover and focus are forced on here so they can be inspected. Focus uses a two-tone ring that stays visible on white, tinted and dark backgrounds.

    Responsive behaviour
    
    
    The component chooses its layout from the width it is given and the number of plans — not from the device. On narrow containers it stops being a table and becomes a two-up comparison: the customer picks which two plans to compare, and the plan summary and group heading stay pinned while they scroll.

    What should hold
    
    
    
      
      
        
    • Long feature names wrap inside the feature column; rows grow, never truncate. Values stay top-aligned with the first line of the label.
      • 
        
    • Long plan names wrap; names bottom-align so plan names, prices and CTAs each sit on a shared line across columns. In paired mode the plan picker wraps the name instead of truncating it like a native select would.
      • 
        
    • Long badges wrap inside their column and push nothing out of line.
      • 
        
    • Missing values render as “Not stated”, distinct from “Not included”.
      • 
        
    • Four plans fit in full/compact; paired mode activates earlier because the rule is width per plan.
      • 
        
    • Price lengths — any pence forces 2 decimal places on every plan; tabular figures keep digits aligned.
      • 
        
    • Additional groups each get a sticky heading; rows no visible plan includes are dropped.
      • 
        
    • Unavailable plan keeps its column (so the customer sees what they can’t have and why) with a disabled CTA and reason.

    Purpose
    
        
    Help a customer choose between two to four mutually exclusive plans whose differences can be expressed against one shared list of features. The matrix exists for comparison: reading across a row to see how plans differ, and down a column to understand one plan.
    
        
    Use it when
    
        
      
          
    • The customer must pick exactly one plan from 2–4 options.
      • 
          
    • Plans share most features and differ by inclusion, limits or service level.
      • 
          
    • The decision benefits from seeing differences side by side, e.g. insurance tiers, broadband speeds, roaming bundles.
      • 
        
    
        
    Don’t use it when
    
        
      
          
    • There is only one product — use a product summary.
      • 
          
    • There are five or more options — use a filterable list, then compare a shortlist.
      • 
          
    • Products have different attributes (a phone vs. a tablet) — there is no shared row to compare against.
      • 
          
    • The goal is promotion rather than decision — use marketing content, not a matrix.
      •

    States
    
        
    Interaction states — default, hover, focus, selected — respond to the customer. System states — recommended, included, conditional, excluded, not stated, disabled — come from data.
    
        
    Recommendation and selection must never look alike: recommendation is accent blue (the business suggests), selection is ink (the customer decided). A recommended plan that is also selected shows both.
    
        
    Conditional values always carry a note. A half-circle with no explanation is a question the customer can’t answer.
    
      
    

      
    
        
    Behaviour
    
        
    Scrolling and sticky headers
    
        
      
          
    • The plan header (name, price, CTA) sticks to the top of the nearest scroll container. The customer can act from anywhere in the list.
      • 
          
    • The current group heading sticks directly beneath it, so “which plan” and “which category” are always visible.
      • 
          
    • Offsets are measured, not hard-coded. Set --cm-sticky-top if a fixed site header sits above the scroll area.
      • 
          
    • A soft shadow appears under the header only while it is stuck.
      • 
          
    • Tables never scroll horizontally. If plans don’t fit, the layout changes instead.
      • 
        
    
        
    Selection
    
        
      
          
    • Single select. Choosing a plan outlines its column and changes its CTA to “Selected”. Choosing another plan moves the selection.
      • 
          
    • Selection persists across layout changes; in paired mode the selected plan is kept in view.
      • 
          
    • In production the CTA normally continues to the next step. The selected state represents a choice already made — a returning customer or a basket — and must still be shown when they come back to compare.
      • 
        
    
        
    Automatic rules
    
        
      
          
    • Rows where no plan includes the feature are dropped (they only add noise).
      • 
          
    • If any price has pence, all prices show 2 decimal places.
      • 
          
    • When any plan has a badge, plan names still align — names bottom-align, badges sit above.
      • 
        
    
      
    

      
    
        
    Responsive
    
        
    Layout is chosen from the component’s own width and its plan count — so the same component works in a full page, a side panel or a modal.
    
        
      
          
    • Full — container ≥ 900px and fits 240px + 170px per plan.
      • 
          
    • Compact — fits 180px + 132px per plan. Smaller type, narrower feature column.
      • 
          
    • Paired — otherwise. Two plans side by side with plan pickers; rows stack label over values.
      • 
        
    
        
    Paired mode is a different presentation of the same data, not a reduced one: every feature remains, and every plan is reachable through the pickers.
    
      
    

      
    
        
    Content rules
    
        
    
          
    
            
    ElementGuideNotes
    
            
              
    Plan name≤ 24 charactersWraps if longer; never truncated. Avoid repeating the product (“Essential”, not “Essential Phone Insurance”).
    
              
    Badge≤ 20 characters“Most popular”, “Your current plan”. Not a sales slogan.
    
              
    Price£11.00 a monthCurrency symbol, amount, period in words. No “only”, no “from” unless genuinely variable.
    
              
    Feature name≤ 40 charactersNoun phrase, sentence case: “Liquid damage”. No question marks or marketing claims.
    
              
    Feature description≤ 60 charactersOne clarifying line. Anything longer belongs in policy documents.
    
              
    Conditional note≤ 30 charactersThe condition itself: “Up to £500”, “Up to 30 days per trip”.
    
              
    Text value≤ 24 charactersUse for genuinely non-binary values: excess, replacement type, claims per year.
    
              
    Group name≤ 24 charactersPlain category: “Loss and theft”. 3–8 rows per group, ≤ 6 groups.
    
              
    Unavailable reason≤ 60 charactersSay why and, if possible, what to do: “Not available for phones over 3 years old”.
    
                
          
    
        
    
        
    Write values from the customer’s side: “Not stated” when data is missing, never a dash — a dash means “not covered” and would misinform.
    
      
    

      
    
        
    Accessibility
    
        
    Semantics
    
        
      
          
    • A native <table> with a <caption>, column headers (th scope="col") for plans, row headers (th scope="row") for features and a heading row per group.
      • 
          
    • Explicit table roles are set on every element so semantics survive the paired layout, where CSS changes their display.
      • 
          
    • It is a data table, not role="grid": screen-reader table navigation already lets users move by row and column, and Tab only stops on things that do something.
      • 
        
    
        
    Keyboard and focus
    
        
      
          
    • Tab order: plan pickers (paired mode) then CTAs, left to right.
      • 
          
    • Focus ring is 3px yellow inside 3px black — visible on white, tinted and dark fills, and replaced by the system colour in forced-colours mode.
      • 
          
    • Sticky regions are short (≈ 130–190px) so they don’t obscure focused content (WCAG 2.4.11).
      • 
          
    • Touch targets are at least 44px tall.
      • 
        
    
        
    Screen readers
    
        
      
          
    • Status icons are aria-hidden; each value has text: “Included”, “Conditional: Up to £500”, “Not included”, “Not stated”.
      • 
          
    • CTA names include the plan: “Choose Extra”, “Selected Complete”.
      • 
          
    • Disabled CTAs use aria-disabled="true", stay focusable, and are described by the visible reason.
      • 
          
    • Selecting a plan or changing the compared pair is announced in a polite live region.
      • 
          
    • In paired mode the caption names the two plans being compared and how many exist; each picker is labelled “First / Second plan to compare”.
      • 
        
    
        
    Colour, zoom and reflow
    
        
      
          
    • Status is conveyed by shape (tick, half-circle, dash) and text, not colour alone.
      • 
          
    • At 400% zoom the container is narrow enough for paired mode — no horizontal scroll (WCAG 1.4.10).
      • 
          
    • Text contrast ≥ 4.5:1; indicator and border contrast ≥ 3:1 against their backgrounds.
      • 
        
    
      
    

      
    
        
    Do / Don’t
    
        
    
          
    
            
    Do
    
            
      
              
    • Order plans cheapest to most comprehensive, left to right.
      • 
              
    • Put the features that differ most between plans near the top of each group.
      • 
              
    • Use conditional values with a short, specific note.
      • 
              
    • Recommend one plan only when you can say why.
      • 
              
    • Keep an unavailable plan visible with its reason.
      • 
              
    • Let the component choose its layout.
      • 
            
    
          
    
          
    
            
    Don’t
    
            
      
              
    • Compare five or more plans.
      • 
              
    • List rows that every plan includes identically just to look generous.
      • 
              
    • Use colour alone to show inclusion.
      • 
              
    • Mark more than one plan as recommended, or make every CTA primary.
      • 
              
    • Show a dash for unknown data.
      • 
              
    • Add horizontal scrolling or hide plans on mobile without a way to bring them back.
      • 
              
    • Nest the matrix inside a container with overflow other than the intended scroll area — sticky headers will stop working.
      • 
            
    
          
    
        
    
      
    

      
    
        
    Configuration
    
        
    The component is driven entirely by data. Values: true included, false excluded, {c: "note"} conditional, {i: "note"} included with detail, a string for a text value, null or missing for not stated.
    

    new ComparisonMatrix(element, {
  caption: "Mobile phone insurance plans",
  plans: [
    { id: "essential", name: "Essential", price: 7 },
    { id: "extra",     name: "Extra",     price: 11 },
    { id: "complete",  name: "Complete",  price: 15,
      available: false, unavailableReason: "Not available for phones over 3 years old" }
  ],
  recommendedPlanId: "extra",       // optional, max one
  recommendLabel: "Most popular",   // optional
  showPrice: true,
  grouped: true,
  selectedPlanId: null,
  groups: [
    { id: "damage", name: "Damage", features: [
      { id: "liquid", label: "Liquid damage",
        values: { essential: false, extra: true, complete: true } },
      { id: "worldwide", label: "Worldwide cover",
        values: { essential: false, extra: { c: "Up to 30 days per trip" }, complete: true } }
    ]}
  ]
});
